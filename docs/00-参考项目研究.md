## 二、逐个拆解：拿什么，丢什么

### 1. urldb —— 数据模型的直接老师

**它做对的事**

- 资源 = `标题 + 多网盘链接 + 链接状态`，而不是"一个下载按钮"。这是资源站最核心的建模洞察。
- 每条链接有独立生命周期：`录入 → 校验 → 有效/失效 → 自动转存 → 定时清理`。
- 同一平台支持多账号（多份转存额度），说明它把"链接失效"当成一等公民在解决。
- 支持 API 批量录入 + Meilisearch 全文检索，规模化路径清晰。

**它没做好的事**

- Go + Nuxt + Postgres + Meilisearch + 独立 PanCheck 服务 = 5 个组件才能跑起来，个人站运维成本过高。
- 后台偏"工具感"，前台偏"数据库感"，缺少内容编排与阅读体验。
- GPL v3 协议，二次分发受限。

**小莫的取舍**：抄它的 `resource_links` 建模与"失效巡检"思路；不抄它的多服务架构，全部收进一个 Next.js 进程 + 一个 cron。

---

### 2. panhub —— 搜索体验的参考

**它做对的事**

- 一次搜索聚合多个来源，按"网盘类型 / 资源类型 / 更新时间"分面筛选。
- 结果卡片信息密度高但克制：标题、来源、网盘标签、时间，四件事，不塞第五件。
- 主打"零广告、轻量部署"，把"干净"本身做成了卖点。

**它没做好的事**

- 纯聚合意味着**内容不在自己手里**，源头一挂站点就空，且无法沉淀 SEO 资产（详情页都是外链跳板）。

**小莫的取舍**：抄它的**分面筛选 UI** 与结果卡片密度；但坚持"每个资源有自己站内的详情页"，把 SEO 资产留在自己域上。

---

### 3. frontend-nav / WebStackPage —— 信息架构的参考

**它做对的事**

- 左侧分类锚点 + 右侧卡片网格，是中文导航站被验证过的最省心结构。
- WebStack 的"图标 + 名称 + 一句话描述"三行卡片，扫读效率极高。

**它没做好的事**

- 只能做"链接簿"，无法承载"版本、大小、平台、更新说明"这类下载站必需字段。
- WebStack 是纯静态，没有后台，更新靠改代码。

**小莫的取舍**：首页沿用"左分类 + 右网格"的肌肉记忆（用户零学习成本），但卡片升级为**资源卡**（含编号、平台、大小、更新时间）。

---

### 4. qiyuan-blog-template —— 内容与资源混合的样本

**它做对的事**

- 用 Astro 做"文章 + 网盘 + 短链 + 资源"四合一，证明**博客式内容页能带动资源页流量**。
- 一键部署（EdgeOne）降低了启动门槛。

**它没做好的事**

- 模板味重，同款站点遍地，品牌辨识度低。
- 内容模型偏博客，资源的结构化字段（平台/版本/校验）不够用。

**小莫的取舍**：采用"**资源详情页 = 结构化字段 + 一段人写的说明**"的混合形态；视觉上坚决不做模板脸（见 DESIGN.md）。

---

### 5. Alist / Cloudreve / zfile —— 分发链路的边界

**它们做对的事**

- Alist：一套 UI 挂载几十种存储，把"目录即接口"做到极致。
- Cloudreve：分享链接 + 提取码 + 过期时间 + 下载计数的完整闭环。
- zfile：目录树的懒加载交互。

**关键结论（很重要）**

> 这三个项目都**自己托管文件**。小莫**不托管资源本体**——成本、带宽、风险都不划算。
> 小莫只托管**元数据 + 封面 + 说明**，下载走网盘直链或自有对象存储的少量小文件。

**可借鉴**：Cloudreve 的"分享链接实体"设计（`token + 提取码 + 过期 + 计数`），小莫用 `resource_links` 表实现同构能力。

---

### 6. 360pb / 苹果CMS —— 反面教材（值得看）

- 360pb：6 star 但结构极简，说明"资源列表"这件事本身不难，难在**持续更新与去重**。
- 苹果CMS v10：2922 star，PHP 生态的资源站标配。它的**采集（爬取入库）+ 自定义字段 + 模板标签**三件套，是中文资源站二十年沉淀下来的运营范式。

**从小莫角度必须避开的坑**

| 坑 | 表现 | 小莫对策 |
|---|---|---|
| 采集泛滥 | 站内 80% 是重复/失效资源 | 入库去重（标题指纹 + 链接哈希），只收人工过审的资源 |
| 模板脸 | 用户记不住你是谁 | 独立视觉系统（DESIGN.md），不用现成主题 |
| 死链堆积 | 用户点开全是"文件已取消" | 链接巡检 cron + 失效自动降权 + 用户举报入口 |
| 无结构 | 只有标题和一段乱码描述 | 强制结构化字段：平台/版本/大小/类型/语言 |

## 三、综合结论：小莫的差异化公式

```
urldb 的数据建模（多链接 + 状态）
  + panhub 的分面搜索体验
  + frontend-nav 的低学习成本布局
  + Cloudreve 的分享链接闭环
  - 所有项目的模板脸
  - 所有项目的多服务运维负担
  = 一个人能维护、用户愿意收藏的资源索引站
```

### 三条不可让渡的产品原则

1. **每个资源都有站内详情页**（不做事外链跳板）——SEO 与信任的根基。
2. **每条下载链接都有状态**（有效 / 失效 / 待校验）——资源站的生命线。
3. **每个资源都有目录编号**（如 `XM-2026-0417`）——可被引用、可被检索、可被存档。

## 四、许可与法律边界（工程视角，非说教）

| 项目 | 协议 | 能否直接改造成小莫 |
|---|---|---|
| urldb | GPL v3 | 改造成本高且需开源衍生，**只借鉴设计，不引代码** |
| panhub | 需查 LICENSE | 前端交互可参考，代码不直接搬 |
| frontend-nav | MIT 系（需确认） | 布局模式可自由借鉴 |
| WebStackPage | MIT | 可借鉴 CSS 思路 |
| Alist / Cloudreve / zfile | AGPL / GPL 系 | **不集成**，避免衍生作品义务 |
| maccms10 | Apache-2.0 | PHP 栈，与选型不符，仅参考字段设计 |

**执行结论**：小莫**从零自建**，只吸收"信息架构与数据模型"这类不受版权保护的思想；不复制任何仓库源码。资源内容层面另行建立来源台账（见 03 文档的运营字段）。
