# 10 · CI 与自动化验收

> 日期：2026-11-03 ｜ 状态：`main` 上每次 push 自动跑构建、单测、烟测、浏览器 e2e

## 一、两个 Job 各管什么

```
verify（约 3 分钟）                 e2e（约 6 分钟，依赖 verify）
├ 类型检查 tsc --noEmit            ├ 装 chromium
├ 单元测试 20 条                   ├ 同样的建库+种子+管理员
├ 建库 → 种子 → 封面               ├ test-auth.mjs    鉴权链路
├ 建管理员                         ├ test-revoke.mjs  会话吊销
├ 构建                             ├ perf.mjs         LCP/CLS/TTFB 预算
└ 起服务 → 9 条路由 + /admin 307   ├ test-guards.mjs 防护链路（最后跑，会锁号）
                                   ├ shot.mjs        三档视口 + 溢出断言
                                   └ 上传截图与 server.log
```

配置文件：[`.github/workflows/ci.yml`](../.github/workflows/ci.yml)

**为什么拆两个 Job**：verify 挂了就不用装浏览器（省 2 分钟）；e2e 挂了你还能确定是构建没问题、是交互坏了。

**关键约定**

| 项 | 值 | 原因 |
|---|---|---|
| `AUTH_SECRET` | CI 专用假值 | 只用于构建与登录流程，不能进生产 |
| 数据库 | 每次从零迁移 + 种子 | 顺带验证"新机器能不能装起来" |
| 浏览器 | `playwright-core` + `playwright install chromium` | 不依赖 CI 机器装 Edge |
| 脚本地址 | `BASE_URL` 环境变量 | 本地默认 127.0.0.1:3100，CI 同值但可覆盖 |

## 二、脚本改成可移植（这轮的额外工作）

原来四个验收脚本都硬编码了本机 Edge 路径：

```js
const EDGE = "C:\\Program Files (x86)\\Microsoft\\Edge\\Application\\msedge.exe";
```

现在统一走 `scripts/lib/browser.mjs`：

```js
export const BASE = process.env.BASE_URL ?? "http://127.0.0.1:3100";
export function launch() {
  const executablePath = process.env.BROWSER_PATH || LOCAL_EDGE;
  return chromium.launch({ executablePath, headless: true });
}
```

- 本地：不设 `BROWSER_PATH` → 用 Edge
- CI：不设 → `playwright install` 装的 chromium（`chromium.launch()` 默认路径）

顺带把脚本从"只打印 JSON"升级成**带断言**：失败时 `process.exit(1)`，否则 CI 永远是绿的。

```
test-auth.mjs    ✗ 鉴权链路断言失败 → exit 1
test-guards.mjs  ✗ 防护断言失败 → exit 1
shot.mjs         ✗ N 个视口出现横向溢出 → exit 1
```

## 三、这轮抓到的真 Bug：迁移器吞语句

本地模拟 CI 的"从零建库"时暴露：

```
pnpm db:migrate   → 应用 001_init.sql（14 条语句）   ← 实际有 15 条
pnpm db:seed      → SqliteError: no such table: main.categories
```

原因：`migrate.mjs` 先按分号切分、再过滤以 `--` 开头的片段。而文件开头是：

```sql
-- 001 初始结构（…）

CREATE TABLE IF NOT EXISTS categories (
```

切分后的第一段同时包含注释和 `CREATE TABLE categories`，被整段丢掉 → `categories` 表从来没建。

更阴的是：`resources` 里的外键指向不存在的 `categories`，SQLite **允许**这种延迟解析，所以建表不报错；只有真正 insert 时才炸。而生产库是最早用 drizzle-kit 建的，一直没暴露。

修法：先按行剔除注释行，再按分号切分。

```js
const sql = raw.split(/\r?\n/).filter(l => !l.trim().startsWith("--")).join("\n");
const statements = sql.split(/;\s*(?:\r?\n|$)/).map(s => s.trim()).filter(Boolean);
```

**教训**：这类"只有全新建库才会犯"的 bug，本地开发环境永远测不出来，只有把 CI 的建库流程在本地跑一遍才能发现。

## 四、本地怎么模拟 CI

```bash
# 1. 用临时库跑一遍迁移链（最关键）
$env:DATABASE_URL="D:\小莫资源站\data\ci-test.db"
pnpm db:migrate
pnpm db:seed
node -e "…检查 categories/resources_fts 是否存在…"
Remove-Item data\ci-test.db*

# 2. 跑三个带断言的验收脚本
node scripts/test-auth.mjs
node scripts/test-guards.mjs   # 会锁账号，跑完重启服务
node scripts/shot.mjs
```

`pnpm test` + `pnpm typecheck` 直接跑就行，与 CI 完全一致。

## 五、CI 不覆盖的部分（别误以为绿了就万事大吉）

| 没覆盖 | 说明 |
|---|---|
| 真实域名 / HTTPS | Caddy 配置只能上机验证 |
| systemd 单元 | `deploy/` 下的文件，CI 不执行 |
| 备份恢复 | 需要真实数据目录，手动季度演练 |
| 视觉审美 | 截图存在 artifact 里，仍需人眼过 |
| 性能指标 | 没接 Lighthouse CI（可后续加） |
| Windows 特有行为 | CI 只跑 Linux；本地才测 Windows |

## 六、性能门禁（不用 Lighthouse）

`scripts/perf.mjs` 直接在 Chromium 里量三项，超预算 `exit 1`：

| 指标 | 预算 | 实测（本地） |
|---|---|---|
| LCP | ≤ 2500ms | 首页 420ms / 分类 236ms / 详情 176ms |
| CLS | ≤ 0.1 | 0.0001 / 0.052 / 0.0001 |
| TTFB | ≤ 800ms | 13 / 17 / 5ms |

**为什么不上 Lighthouse**：lhci 要装整套（约 50MB+），跑一次全量审计 30 秒起；
我们只需要"别退化"，Playwright + `PerformanceObserver` 已经够，且和 CI 里的浏览器是同一个。

> 分类页 0.052 的 CLS 来自客户端筛选的 Suspense fallback（骨架 → 卡片）。仍在预算内，
> 真要压到 0 需要把筛选改成纯 CSS（`:has()`）或把参数改成路径段。

## 七、下一步可以加的

1. **Lighthouse CI**：首页/详情页跑一次，LCP > 2.5s 就红
2. **依赖审计**：`pnpm audit --prod` 每周一次定时任务
3. **部署工作流**：`workflow_dispatch` 手动触发 `deploy.sh`（SSH 到 VPS）
4. **自动 tag**：合并到 main 后按 commit 生成版本号，方便回滚
