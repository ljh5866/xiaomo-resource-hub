# 11 · 会话吊销与账号运维

> 日期：2026-11-03 ｜ 状态：改密码/强制下线后，旧 JWT 在后台立即失效

---

## 一、为什么 JWT 需要"吊销"

JWT 是无状态的：签发后服务端不记录，所以**天然无法撤回**。默认情况下，改密码、封号、员工离职，
旧 token 仍然有效到过期（我们设的是 30 天）。这是纯 JWT 方案最常见的漏洞。

行业里有三种解法：

| 方案 | 代价 | 适用 |
|---|---|---|
| 每请求查库校验会话 | 每个请求一次 DB | 内部系统，量小 |
| Redis 黑名单 | 多一个组件 | 多实例、高并发 |
| **版本号（本文采用）** | 只在需要保护的入口查一次 | 单机、后台类入口 |

## 二、实现

```
users.token_version  (int, 默认 0)
        │
        ├─ 登录时写入 JWT：token.ver = 当前值
        └─ 后台入口校验：JWT.ver === DB.token_version ?
                ├─ 相等 → 放行
                └─ 不等 → 渲染「会话已失效」页（不 redirect，原因见下）
```

| 件 | 位置 |
|---|---|
| 迁移 | `src/db/sql/003_token_version.sql` |
| JWT 写入/读取 | `src/lib/auth/config.ts`（`jwt` / `session` callback） |
| 校验 | `src/lib/auth/index.ts` → `getSessionUser()` |
| 落地页 | `src/components/auth/session-revoked.tsx` |
| 命令 | `pnpm user:revoke <email>` |

```bash
pnpm user:revoke admin@xiaomo.local
# ✓ admin@xiaomo.local 的会话版本 2 → 3
#   该账号所有已登录设备会在下次请求后台时被要求重新登录。
```

改密码场景建议连用：

```bash
pnpm user:add <email> <新密码> --admin   # 覆盖密码
pnpm user:revoke <email>                # 顺手踢掉旧会话
```

## 三、踩到的坑：流式渲染下 `redirect()` 不落地

第一版在 admin layout 里写 `if (!user) redirect("/login")`，结果实测：

```
after-revoke → status 200, url 仍是 /admin
body 里只有 Header 和 Footer，没有任何后台内容
```

原因：Next 的流式 SSR 已经发出了 `200` 与部分 HTML，此时嵌套 layout 抛出的 `NEXT_REDIRECT`
已经没有机会变成 HTTP 302，只能靠客户端脚本补跳；页面骨架先落地，于是用户看到"空后台"。

**修法**：不 redirect，直接渲染一个明确的落地页：

```tsx
const session = await auth();
if (!session?.user) redirect("/login?next=/admin");   // 压根没登录 —— 流开始前就跳，安全
const user = await getSessionUser();
if (!user) return <SessionRevoked />;                 // 有 JWT 但版本不对 —— 渲染说明页
```

判断逻辑也因此分成两种情况，语义更清楚：

| 状态 | 判据 | 表现 |
|---|---|---|
| 未登录 | `auth()` 无 user | 302 → `/login?next=…` |
| 会话被吊销 | 有 user 但版本不符 | 200 → 「会话已失效」页 + 重新登录/清除会话 |

## 五、这个方案没覆盖的

| # | 场景 | 说明 |
|---|---|---|
| 1 | 公网页面仍认旧 JWT | 首页/详情页不查库（否则就不能静态化）。但它们与权限无关 |
| 2 | 同一版本内无法单独踢某台设备 | 吊销是"全部设备一起下线"，没有按设备粒度 |
| 3 | 生效点是"下次请求后台" | 正在打开的后台页面不会立刻自毁（下次导航才检查） |
| 4 | 多实例时需共享 DB | 版本存在 SQLite 里，多实例共用一个库即可；换 Postgres 同理 |

> 结论：对"单人/小团队维护的资源站"够用；要按设备管理会话，就得上服务端 session 表。
