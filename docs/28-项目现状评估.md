## 2. 问题清单（按严重度）

### P0 · 用户数据已公开（必须今天处理）

`tmp-supabase-users.csv` **被 git 跟踪并已推到 public 仓库**（提交 `c12728a`），含 34 行 `id,email,password_hash,created_at,meta`。

实证：
```
GET https://raw.githubusercontent.com/ljh5866/xiaomo-resource-hub/main/tmp-supabase-users.csv
→ 200，9,570 B，header: id,email,password_hash,created_at,meta
```

bcrypt 哈希不可逆，但**可离线爆破**——尤其那批用户很可能复用密码。处置：

```bash
# 1) 移出跟踪 + 加规则（本地）
git rm --cached tmp-supabase-users.csv
printf 'tmp-*.csv\ntmp-*.mjs\n' >> .gitignore
git add .gitignore && git commit -m "chore: 移除误提交的用户导出文件并忽略 tmp 产物"
git push

# 2) 清洗历史（必须，否则旧提交里永远能看到）
#    安装 git-filter-repo 后：
git filter-repo --path tmp-supabase-users.csv --invert-paths --force
git remote add origin https://github.com/ljh5866/xiaomo-resource-hub.git
git push --force --all && git push --force --tags
```

```bash
# 3) 线上兜底：吊销全部会话 + 通知这 33 位用户改密码
cd /var/www/xiaomo
sqlite3 data/app.db "UPDATE users SET token_version = token_version + 1;"
sudo systemctl restart xiaomo
```

> 注：GitHub 的已删除对象仍可能被 fork / 缓存 / 第三方镜像保留，**改密码才是真正的止血**。

顺带：`tmp-audit.mjs`、`tmp-mk.mjs` 也在仓库里（无敏感内容，属于"脏"，一起清）。

### P1 · SEO 语义错误：软 404

| URL | 现状 | 应为 |
|---|---|---|
| `/r/definitely-not-exist` | **200** + 34 KB「资源不存在」页 | 404 |
| `/c/not-a-category` | **200** + 50 KB 空页 | 404 |
| `/t/not-a-tag` | 404 ✓ | — |

根因：`src/app/(front)/r/[slug]/page.tsx` 的 `generateMetadata` 里写的是
`if (!data) return { title: "资源不存在" }` —— 返回正常 metadata，页面组件稍后才 `notFound()`，此时流式响应已发出 200 头，改不了状态码。

修法（两处，各一行）：

```ts
// generateMetadata 内
if (!data) notFound();      // 取代 return { title: "资源不存在" }
```

分类页 `/c/[category]` 同理。搜索引擎拿到 200 会把空页当正常内容收录，白烧抓取预算。

### P1 · 热度体系空转

- `view_count` 字段存在、详情页会读，但**全库没有一条 `UPDATE resources SET view_count`** → 永远 0。
- `download_events` 只有写入（`/go/[id]` 有 INSERT），本地 0 条。

影响：首页/分类页的"热度"排序、后台看板、运营判断全部没有数据源。建议：详情页命中时 `UPDATE ... view_count = view_count + 1`（或用 `download_events` 的 1 分钟去重聚合，避免写放大）。

### P1 · 软件工具分类是空的

四个分类挂了入口，`software` 实际 **0 条**（本地/线上都 0）。访客点进去是空列表 —— 比"没有这个分类"更伤。
两个选择：① 补内容（导入脚本已具备，改 `--category software` 即可）；② 先 `is_visible = 0` 隐藏入口，等内容到位再开。

### P2 · 性能：瓶颈在链路，不在应用

- 应用侧：服务端渲染 ≈ 350ms（TTF 1032 − 握手 680），对一个 2C2G + SQLite 的站算正常。
- 链路侧：**TCP 343ms / TLS 680ms** → 单程 RTT 340ms，明显高于香港 CN2 应有的 30–60ms。首屏 2s 里有 1s 花在握手。
- 图片侧：24 张封面各 ~35 KB，**每张都过 Node 进程**（1.35s/张，冷缓存），Caddy 目前只加 `Cache-Control`，没有 `file_server` 直出。

按性价比排序：
1. **Caddy 直出 `/files/*`**（把 `handle_path /files/*` 指到 `/var/www/xiaomo/data/uploads`，`reverse_proxy` 只剩动态请求）——零成本，图片响应从 ~1.35s 降到几十 ms。
2. **加 CDN**（Cloudflare 免费版即可）：HTML `s-maxage=60` 已就绪，静态资源 immutable 已就绪，接上就是纯收益。
3. **换线路**：如果 RTT 长期 340ms，考虑轻量的"全球加速"或换 CN2/优化线路（这会真正解决首屏 1s 的握手）。
4. 搜索页 HTML 254 KB 偏大，可对结果卡做懒渲染或减少每页条数。

### P3 · 数据与内容

### P4 · 工程债

## 4. 结论

这不是一个"还没做完"的项目，而是一个**已经能跑、但基础设施细节还没收紧**的项目。
功能层面的坑基本都填过了（退出登录、头像、重复卡片、后台 404、导入路径），剩下的问题集中在三类：

1. **安全事件**：公开仓库里的用户导出文件 —— 唯一真正紧急的事。
2. **语义正确性**：软 404、空分类、0 埋点 —— 影响搜索引擎和运营判断，但都好修。
3. **物理距离**：RTT 340ms 是香港轻量 → 大陆的常态，应用侧再优化也突破不了，需要 CDN 或换线路。

把 P0 + P1 收掉之后，这个项目的工程质量足以支撑"内容做到 5000 条"的规模。
