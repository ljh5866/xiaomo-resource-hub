# 13 · 举报链路与后台写操作防护

> 日期：2026-11-03 ｜ 状态：游客可举报 → 后台处理；所有后台写操作加了服务端鉴权

---

## 一、举报怎么走

```
详情页「链接失效？举报」
    ↓ 原生 <dialog> 表单（URL 选择 / 问题类型 / 可选联系方式）
POST /api/report   ← 免登录，限流 5 次/小时/IP
    ↓
reports 表（status=open，记录 link_id 便于精确到某条链接）
    ↓
/admin/reports 列表：待处理优先，可「标记已处理」或「忽略」
```

| 件 | 位置 |
|---|---|
| 弹窗 | `src/components/resource/report-dialog.tsx` |
| 接口 | `src/app/api/report/route.ts`（白名单 reason + 存在性校验 + 限流） |
| 后台 | `src/app/admin/reports/page.tsx` |
| 动作 | `src/lib/admin/actions.ts` → `handleReport(id, status)` |
| 表 | `reports(id, resource_id, link_id, reason, contact, status, created_at, handled_at)` |

**为什么不要求登录**：举报是给偶发访客用的，加登录墙等于放弃这个渠道。
用限流 + 服务端白名单防滥用就够了。

## 二、顺手补的一个真窟窿：后台写操作没有鉴权

之前 `saveResource` / `setStatus` / `deleteResource` / `importCsv` 只靠 middleware 拦 `/admin` 页面。
问题是：**Server Action 本质是一个 POST 端点**，一旦它的调用链不在 `/admin` 路径下（或将来复用到别处），
middleware 就管不到 —— 这是"只靠路由守卫"的典型漏洞。

修法：在每个导出动作最前面加一次服务端校验。

```ts
async function guard(): Promise<ActionResult | null> {
  const admin = await requireAdmin();
  return admin ? null : { ok: false, message: "需要管理员登录" };
}

export async function deleteResource(id: number) {
  const denied = await guard();
  if (denied) return denied;
  …
}
```

`requireAdmin()` 还会校验 `token_version` —— 所以「改密码 / 强制下线」对写操作同样立即生效。

## 四、还没做的

| # | 项 | 说明 |
|---|---|---|
| 1 | 举报 → 自动降权 | 同一链接被举报 ≥3 次可自动 `status=invalid`，现在要人工判断 |
| 2 | 处理通知 | 填了联系方式也没有回信渠道（需要 SMTP / TG Bot） |
| 3 | 投稿入口（提交新资源） | 计划里 V1.1 的另一半，表单结构可复用举报的写法 |
| 4 | 举报去重 | 同一人对同一链接重复点会插入多条（限流兜住了数量） |
| 5 | 后台分页 | 举报列表现在取最近 100 条，行数多了要加筛选 |
