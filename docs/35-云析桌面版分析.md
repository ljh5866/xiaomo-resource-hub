# 35 · 云析 YunX-Desktop 项目分析

> 仓库 <https://github.com/tidain/YunX-Desktop>（AGPL-3.0），分析于 2026-11-28。
> 目的：对照我们自己的桌面端，找出「该补什么、能抄什么、别学什么」。

## 一、它是什么

Windows 桌面端的**网盘/视频/磁力 下载器**：粘贴分享链接 → 浏览内容 → 高速下载，全程本机完成。

| 维度 | 值 |
|---|---|
| 语言 / UI | **Kotlin + Compose Multiplatform (Desktop) + Material 3** |
| 网络 | OkHttp 4.12 |
| 内嵌浏览器 | **JCEF 132**（真 Chromium，约 100MB+） |
| 持久化 | sqlite-jdbc + `java.util.prefs` |
| 原生桥接 | JNA + 自编 `darkmode.dll`（C++，托盘配色用） |
| 打包 | Gradle + **jlink + jpackage** + Inno Setup |
| 分发 | 便携版（文件夹）+ 安装版（Inno Setup） |
| 规模 | 270 个文件，其中 Kotlin 约 200 个 |

值得抄的设计：

```kotlin
// 慢连接抢占：阈值 = max(用户下限, 本任务平均单连接速度 / 2)
fun preemptFloorBps(avgPerConnBps: Long): Long = maxOf(preemptMinBps, avgPerConnBps / 2)
```

```kotlin
// Content-Range 必须严格校验 —— 服务端返回的区间和请求的不一致就重试
fun matches(value: String?, requestedStart: Long, requestedEnd: Long?): Boolean {
    val range = parse(value) ?: return false
    if (range.start != requestedStart) return false
    return requestedEnd == null || range.end == requestedEnd
}
```

### 登录（三种方式并存）

1. **内嵌 JCEF 浏览器**（推荐）——这是它能拿到 httpOnly cookie 的根本原因
2. **一键导入本机浏览器 Cookie**（Chrome/Edge/360/QQ/搜狗/Opera/Brave/Vivaldi + Firefox）
3. **手动粘贴**

它的 cookie 导入和我们写的 `cookies.rs` 几乎一致（DPAPI + `v10`/`v20` 判断）。

### 视频解析（7 家）

抖音 / 快手 / 微博 / 小红书 / B站 / AcFun / Pixiv。
B 站要登录取高清，DASH 分轨下载后用 ffmpeg 合轨。

播放器两条路：**ffplay 边下边播**（首选）+ JavaFX Media（兜底），FFmpeg 约 50–90MB **不随包发布**、按需下载。

### 其它

- 磁力 / BT / ed2k（交给 Gopeed 引擎）
- GitHub 仓库浏览 + README 渲染 + 五镜像自动测速
- 浏览器扩展（MV3）：嗅探页面资源、接管浏览器下载、本机回环 HTTP + 随机 token
- 通知中心 toast 进度条
- 多账号 / 加密备份 / 深色模式 / 托盘 / 剪贴板检测

## 三、和我们的桌面端对照

| 维度 | 云析 | 我们（小莫桌面端） |
|---|---|---|
| 技术栈 | Kotlin + Compose（JVM） | **Rust + Tauri 2 + React** |
| 渲染 | Skia 自绘（无浏览器内核） | WebView2（系统自带） |
| 安装包 | jlink 裁剪后的 JRE + 应用，**预计 80–150 MB**（未实测） | **2.68 MB** |
| 冷启动 | JVM 启动 + Compose 初始化 | 快（系统 WebView2 预热） |
| 网盘支持 | **10 家** | **1 家**（夸克） |
| 视频解析 | **7 家** | 无 |
| 磁力/BT | ✅ Gopeed | 无 |
| 分片下载 | ✅ 完整（抢占/续传/校验/限速） | ⚠️ 只有单连接流式 |
| 内嵌登录 | ✅ JCEF（Chromium） | ✅ WebView2 |
| 浏览器 cookie 导入 | ✅ | ✅（DPAPI 那套） |
| 账号体系 | 本地多账号 | **跟站点账号打通**（可跨设备同步收藏） |
| 内容来源 | 用户粘贴链接 | **站点资源库（1043 条）** + 分享解析 |

**核心差异**：它做「通用下载器」，我们做「资源站的客户端」。它强在协议覆盖，我们强在内容和账号。

## 四、最值得抄的四件事

### 1. 分片下载的「慢连接抢占」

我们现在是单连接 `reqwest` 流式写文件。夸克直链**按连接限速**，单连接就是几十 KB/s～2 MB/s。
云析的做法：开 N 个分片并发，**看门狗每周期扫一遍**，某片速度低于 `max(12KB/s, 平均/2)` 且持续 15 秒 → 抢占、重新分配区间。

### 2. `Content-Range` 严格校验

服务端可能返回比你请求更短的区间（甚至忽略 Range 返回整包）。
云析要求 `start == requestedStart && end == requestedEnd`，否则重试该片 —— 这是「下到一半文件损坏」的根因防呆。

### 3. 分片级 SHA-256

写入时增量算摘要，合并时逐片重算比对，不一致就拒绝保存。**不额外读盘**。

### 4. 临时转存清理策略

它的规则：**百度 / 迅雷取链后立刻清理；夸克保留到下载完成或删除任务后清理**。
我们现在转存的文件会一直堆在用户夸克根目录 —— 这是必须补的。

## 五、不该学的三件事

| 做法 | 为什么不学 |
|---|---|
| JCEF 内嵌 Chromium | 直接把安装包抬到 100MB+，而 WebView2 是系统自带的，零成本 |
| Compose 自绘 UI | 排版能力弱于 HTML/CSS，改一版界面成本高 |
| jlink + jpackage + Inno Setup 三件套 | 我们 Tauri 一条命令出 2.68MB 安装包 |

## 六、结论：我们的下一步（按投入产出）

| 优先级 | 事项 | 参考云析的什么 | 工作量 |
|---|---|---|---|
| **P0** | 分片并发 + 断点续传 | `ChunkDownloader` + `HttpRangePolicy` | 2–3 天 |
| **P0** | 转存文件清理（下载完删掉） | 它的「临时转存清理」规则 | 半天 |
| P1 | 多网盘支持（UC / 迅雷 / 123） | 每家一个 `*Api.kt` 的结构 | 每家 1–2 天 |
| P1 | 下载队列 / 暂停继续 | `DownloadManager` 的任务状态机 | 1–2 天 |
| P2 | 分片 SHA-256 校验 | `DownloadSaver` | 1 天 |
| P2 | 剪贴板识别分享链接 | 它的「剪贴板分享链接检测」 | 2 小时 |
| P3 | 视频解析 | 与站点定位不符，暂不做 | — |

**一句话**：它证明了「内嵌浏览器登录 + 本机直连下载」这条路可行（我们刚走的同一条），
接下来该补的是**下载引擎的工程质量**（分片、续传、校验、清理），而不是铺更多网盘。
